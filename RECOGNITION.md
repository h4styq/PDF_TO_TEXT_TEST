# Универсальное распознавание УПД / счёт-фактур

Цель — **один конвейер** для любых PDF одного типа: типовая таблица УПД (15 граф), разные наименования, **от 1 до 100** позиций, несколько страниц. Отдельные «эталоны» и кнопки сверки **не используются**.

Подробности реализации: `InvoicePdfToSheet.gs`, константы `UPD_ROW_SEQ_MAX`, `CANONICAL_UPD_HEADERS`, `SCRIPT_VERSION`.

---

## 1. Что считаем «похожим документом»

| Входит в область | Не входит (нужна доработка) |
|------------------|-----------------------------|
| УПД / счёт-фактура РФ, таблица с графами как в `CANONICAL_UPD_HEADERS` | Накладные без блока «наименование + 796 + шт + суммы» |
| Скан или текстовый PDF, кириллица + латиница в номенклатуре | Чисто рукописные без OCR |
| Строки: **№ п/п** → **наименование** → **ОКЕИ 796** → **шт** → кол-во → цены → НДС → страна | Таблицы только с 3–4 колонками без ОКЕИ |

**Инвариант строки товара (граница «это позиция УПД»):**

- `looksLikeOcrUpdProductRowLine_`: начинается с `1–99`, далее текст, есть **`796`** и **`шт`**, есть суммы или ставка НДС.
- Либо та же логика после разбиения склеенной OCR-строки (`splitLineByOcrRowNumbers_`).

**Инвариант граф (куда кладём данные):**

Всегда **15 колонок** `CANONICAL_UPD_HEADERS` (№ п/п … рег. номер декларации). Токены раскладываются смысловым маппером `semanticMapGoodsRow_`, не «как попало по TAB».

## 2. Поток данных

```
PDF
  → pdfToExtracted_(mode: gemini | ocr)
  → parseInvoiceData_
       шапка: продавец, счёт-фактура, платёжный документ, основание
       таблица: pickBestOcrTable_ → normalizeGoodsTableRows_
  → лист «Счета_фактуры»
```

### Запуск

| Меню | Режим |
|------|--------|
| Загрузить из папки (Gemini) | Gemini → OCR.space; пауза ~20 с |
| Загрузить из папки (OCR.space) | Только OCR.space, без паузы |

Ключи: `GEMINI_API_KEY`, `OCR_SPACE_API_KEY` (свойства скрипта).

**Другие API для PDF:** обзор бесплатных и условно-бесплатных вариантов — [PDF_OCR_ALTERNATIVES.md](PDF_OCR_ALTERNATIVES.md).

## 3. Выбор источника таблицы (`pickBestOcrTable_`)

Два кандидата:

1. **Блок УПД** — текст между заголовком «наименование…» и «Всего к оплате».
2. **Построчный OCR** — `parseOcrProductRowsOnly_` по всему тексту.

**Правила выбора (минимизация ошибок):**

- Берётся вариант с **большей оценкой** `scoreOcrTableQuality_`.
- Блок УПД **штрафуется**, если у соседних строк **одинаковое начало наименования** (типичный баг: одна позиция размазана на несколько строк).
- Построчный вариант **бонусируется**, если строк **больше**, чем в блоке (склеенные / многостраничные УПД).
- Оценка растёт с числом строк до **100**, без искусственного потолка «8 строк».

---

## 4. Ядро обработки строк (без привязки к поставщику)

Порядок в `normalizeGoodsTableRows_`:

| Шаг | Функция | Назначение |
|-----|---------|------------|
| 0 | `parseOcrProductRowsOnly_` + `supplementOcrProductRowsFromFlat_` | Пересборка из полного текста; добор пропущенных № (2-я страница); лимит № **1…100** |
| 1 | `extractDocumentSeqFromCells_` | Сохранить **№ п/п из документа**, не перенумеровывать «по порядку вывода» |
| 2 | `alignRowToCanonicalGoodsColumns_` | Если в ячейках склеены метрики — `tokenizeOcrProductLine_` |
| 3 | `repairScrambledOcrRow_` | В т.ч. `repairRowFromEmbeddedOcrTokens_` если в наименовании остались `796 шт` и суммы |
| 4 | `stripProductNameAtOkeiMarker_` | Наименование **только до** `796` / сумм |
| 5 | `enrichProductNameFromFlat_` | **Длиннее** фрагмент из OCR по № строки и (опционально) артикулу в скобках — **любой** товар |
| 6 | `normalizeGoodsTableRowOrderGeneric_` | Доставка vs товар; сортировка по **№ п/п** |
| 7 | `repairGenericMappedRow_` | Суммы, НДС, «без акциза», страна |
| 8 | `finalizeDocumentRowNumbers_` | Итоговый порядок по № из УПД |

**Многостраничность:** после «Всего к оплате» разбор **не обрывается**, если ниже снова заголовок таблицы или строка `looksLikeOcrUpdProductRowLine_`.

---

## 5. Границы наименования

- **Начало:** после № п/п (в OCR или в документе).
- **Конец:** перед `\s796\s*шт` или первой суммой `1 234,56`.
- **Расширение:** `expandProductNameFromDocumentFlat_` — ищет в плоском тексте **более длинный** фрагмент той же строки (по № и до `796`), без словаря брендов.
- **Максимум символов:** `PRODUCT_NAME_MAX_LEN` (280).

---

## 6. Фильтр мусора

Строка **не попадает** в лист, если `isGarbageMappedRow_`: нет ни ОКЕИ, ни кол-ва, ни сумм; или это шапка/«Всего к оплате»; или наименование — только цифры.

**Верхний лимит:** `MAX_GOODS_ROWS_PER_PDF` = **100** (защита от бесконечного OCR-мусора).

---

## 7. Исключения (vendor-слой — сужать со временем)

`applyVendorDocumentRepairs_` вызывается **только** при явных маркерах в тексте (Электромонтаж, ЛинкМаг и т.д.). Это **не** часть универсальной схемы; новые УПД должны проходить **только ядром** (раздел 4).

---

## 8. Ожидаемая точность и ограничения

| Ситуация | Поведение |
|----------|-----------|
| 90% типовых УПД, TAB или ровные пробелы | Блок УПД или построчный OCR, метрики в графах |
| Склеенная строка «1 … 2 … 50 …» | `splitLineByOcrRowNumbers_` |
| 5-я позиция на стр. 2 | `supplementOcrProductRowsFromFlat_`, `ocrTableContinuesAfterTotals_` |
| OCR обрезал начало («Lech» вместо «Logitech») | В лист попадёт **максимум из OCR**; полное имя только если оно есть в тексте API |
| >100 строк в PDF | Обрезка до 100 + запись в лог |

**Не гарантируется:** 100% совпадение с PDF, если OCR/Gemini **не вернули** фрагмент текста (нужен повторный прогон или другой API).

## 9. Проверка версии

В редакторе Apps Script: **Ctrl+F** → `SCRIPT_VERSION` (например `2026-05-20-upd-generic-bounds`).

После правок: `clasp push`, обновить страницу таблицы (F5), прогнать папку с PDF.
